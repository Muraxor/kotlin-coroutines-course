# Контекст, потоки и диспетчеры

**Источник:** [официальная документация Kotlin / JetBrains](https://kotlinlang.org/docs/coroutine-context-and-dispatchers.html). Ниже — выборочный учебный перевод и объяснение ключевых положений главы, а не полный текст документации. Примеры адаптированы для задач этого проекта. Чтобы сверить детали поведения, перейди по ссылкам у каждого раздела.

## Контекст

Контекст корутины содержит Job, диспетчер и необязательные элементы вроде CoroutineName. Ребёнок наследует элементы родителя, но получает собственный Job, связанный с ним. Новый элемент того же типа заменяет старый: имя child переопределяет parent, однако само родительство сохраняется.

[Официальный раздел](https://kotlinlang.org/docs/coroutine-context-and-dispatchers.html#job-in-the-context).

## Диспетчер и поток

Dispatcher определяет, где выполняются участки кода. Dispatchers.Default рассчитан на вычислительную работу; Dispatchers.IO — на блокирующий ввод-вывод JVM. Имя конкретного потока может измениться после приостановки, а может остаться прежним. Поэтому тестируй результат и жизненный цикл, а не обязательную смену имени потока.

[Официальный раздел](https://kotlinlang.org/docs/coroutine-context-and-dispatchers.html#dispatchers-and-threads).

## withContext

withContext выполняет блок в другом контексте и возвращает его результат после завершения. Это естественная граница: блокирующее чтение на IO, вычисление на Default, итог у вызывающего кода. launch для такого случая неудобен: он возвращает Job и не отдаёт значение, а отдельный scope может оставить работу после возврата функции.

[Официальный раздел](https://kotlinlang.org/docs/coroutine-context-and-dispatchers.html#jumping-between-threads).

## Диагностика и ограничение

CoroutineName помогает читать логи нескольких одновременных операций. Добавь его вместе с именем потока, чтобы увидеть разницу между логической задачей и исполнителем. limitedParallelism ограничивает число одновременно исполняемых блоков на представлении диспетчера, но не является общим замком для данных и не ограничивает всю длительность suspend-операции.

[Официальный раздел](https://kotlinlang.org/docs/coroutine-context-and-dispatchers.html#naming-coroutines-for-debugging).

## Разобранный пример

```kotlin
suspend fun readAndCount(): Int {
    val text = withContext(Dispatchers.IO) { blockingRead() }
    return withContext(Dispatchers.Default) { text.length }
}
```

После блокирующего чтения на IO вычисление идёт на Default; вызывающий получает Int. blockingRead — условная функция-заглушка.

## Как проверить себя в задачах

Открой [задачи](TASKS.md) и запускай каждую отдельно. В журнале смотри на порядок событий, фактический результат и имя потока. Сравнивай только гарантированный порядок: завершение ребёнка до выхода из его scope, результат после await, cleanup до cancelAndJoin. Если поведение удивило, обсудим конкретный вывод в чате.
