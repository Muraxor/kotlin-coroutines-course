# Flow: холодные потоки и операторы

**Источник:** [официальная документация Kotlin / JetBrains](https://kotlinlang.org/docs/flow.html). Ниже — выборочный учебный перевод и объяснение ключевых положений главы, а не полный текст документации. Примеры адаптированы для задач этого проекта. Чтобы сверить детали поведения, перейди по ссылкам у каждого раздела.

## Холодный источник

Обычный flow начинает выполнять тело только при collect. Повторный collect обычно запускает источник заново. emit отправляет очередное значение; collect принимает его. Это удобно для описания последовательности загрузки, которую разные вызовы могут запускать независимо.

[Официальный раздел](https://kotlinlang.org/docs/flow.html#flows-are-cold).

## Преобразование и завершение

map, filter и take строят новую цепочку, но сами не запускают работу. Терминальные операции collect и toList запускают её. take ограничивает количество элементов и позволяет закончить сбор потенциально бесконечного источника. Ожидай именно значения и завершение, а не конкретное время каждого emit.

`distinctUntilChanged` убирает повторения **соседних** одинаковых значений. Если между двумя одинаковыми значениями было другое, второе останется. В итоговой задаче это позволяет убрать повторный замер, не теряя более позднее новое значение. [Официальное описание оператора](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/distinct-until-changed.html).

[Официальный раздел](https://kotlinlang.org/docs/flow.html#intermediate-flow-operators).

## Буфер и последняя версия

По умолчанию стадии Flow работают последовательно. buffer позволяет производителю продвигаться, пока потребитель занят. conflate допускает пропуск промежуточных значений для медленного получателя; collectLatest отменяет обработку старого значения, когда приходит новое. Выбирай по контракту: телеметрии может быть нужен каждый пакет, а поиску — последний запрос.

[Официальный раздел](https://kotlinlang.org/docs/flow.html#buffering).

## Ошибки, контекст и отмена

catch видит исключения, возникшие выше него по цепочке, но не ловит ошибку в нижнем collect. flowOn меняет контекст upstream. Отмена коллектора распространяется к источнику и запускает его finally. Эти границы особенно важны в длинном конвейере: расположение оператора меняет поведение.

[Официальный раздел](https://kotlinlang.org/docs/flow.html#flow-exceptions).

## Разобранный пример

```kotlin
flow { for (n in 1..5) emit(n) }
    .filter { it % 2 == 1 }
    .map { it * 10 }
    .collect { println(it) }
```

Вывод: 10, 30, 50.

## Как проверить себя в задачах

Открой [задачи](TASKS.md) и запускай каждую отдельно. В журнале смотри на порядок событий, фактический результат и имя потока. Сравнивай только гарантированный порядок: завершение ребёнка до выхода из его scope, результат после await, cleanup до cancelAndJoin. Если поведение удивило, обсудим конкретный вывод в чате.
