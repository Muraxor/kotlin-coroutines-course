# Общие данные: гонки, атомики и Mutex

**Источник:** [официальная документация Kotlin / JetBrains](https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html). Ниже — выборочный учебный перевод и объяснение ключевых положений главы, а не полный текст документации. Примеры адаптированы для задач этого проекта. Чтобы сверить детали поведения, перейди по ссылкам у каждого раздела.

## Потеря обновлений

Операция counter++ состоит из чтения, вычисления и записи. Два потока могут прочитать одно и то же старое значение и записать одинаковый новый счётчик. Поэтому результат меньше ожидаемого. Удачный единичный прогон не доказывает отсутствие гонки; проверяй инвариант многократно.

[Официальный раздел](https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html#the-problem).

## volatile и атомики

volatile помогает с видимостью отдельных чтений и записей, но составной increment по-прежнему не атомарен. AtomicInteger.incrementAndGet выполняет увеличение как одну потокобезопасную операцию. На JVM это простой выбор для счётчика без сложного связанного состояния.

[Официальный раздел](https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html#volatiles-are-of-no-help).

## Mutex и инварианты

Mutex.withLock защищает критическую секцию. В задаче склада проверка остатка и уменьшение должны быть под одним lock, иначе два клиента могут одновременно увидеть доступный товар. Все пути чтения и записи, влияющие на инвариант, должны следовать одному правилу. Не держи lock вокруг длинного внешнего вызова без необходимости.

[Официальный раздел](https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html#mutual-exclusion).

## Меньше общего состояния

Не всегда нужен lock: дочерние корутины могут считать локальные суммы и вернуть их родителю, а тот объединит результат. Другой подход — один владелец изменяемого состояния. Так проще понять, где можно менять данные. Перед выбором механизма запиши инвариант: например, общий баланс не меняется, а остаток склада не отрицателен.

[Официальный раздел](https://kotlinlang.org/docs/shared-mutable-state-and-concurrency.html#thread-confinement-coarse-grained).

## Разобранный пример

```kotlin
val mutex = Mutex()
var stock = 10
suspend fun reserve(count: Int): Boolean = mutex.withLock {
    if (stock < count) false
    else { stock -= count; true }
}
```

При двух конкурентных резервах по 7 успешным станет только один.

## Как проверить себя в задачах

Открой [задачи](TASKS.md) и запускай каждую отдельно. В журнале смотри на порядок событий, фактический результат и имя потока. Сравнивай только гарантированный порядок: завершение ребёнка до выхода из его scope, результат после await, cleanup до cancelAndJoin. Если поведение удивило, обсудим конкретный вывод в чате.
